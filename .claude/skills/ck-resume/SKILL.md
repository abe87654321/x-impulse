# ck-resume — 读交接检查点并先验真

## 核心规则

**检查点是上一个会话的声明，不是事实。** 先验证，再使用。

仓库可能在检查点写下之后被改动过 —— 别的会话推了提交、用户手工改了文件、
分支切走了。**不校验就接续，等于从一个想象的状态开始工作**，而且错误会一路传下去。

## 步骤

### 1. 读检查点

```bash
cat .kb/checkpoint.md
```

文件不存在 → 告诉用户没有检查点，然后按 `SETUP.md` 正常开工，**不要编造一个**。

### 2. 校验锚点（强制，不可跳过）

```bash
git rev-parse HEAD
git status --short
```

对照检查点表头里的 `HEAD` 与"工作区"两行：

| 情况 | 处理 |
| --- | --- |
| HEAD 一致、工作区状态一致 | 检查点**有效**，继续第 3 步 |
| HEAD 一致、工作区多出改动 | 检查点**基本有效**但有未记录的改动。先 `git status` 和 `git diff` 看清楚再动，并告知用户 |
| **HEAD 已变** | 检查点**已过期**。用 `git log --oneline <检查点HEAD>..HEAD` 看中间发生了什么，把结论告诉用户，**第 1、4 节一律不得直接采信** |
| 分支与检查点不同 | **停下来问用户**，不要自行切分支 |

### 3. 验证客观状态 —— 实跑，不信记录

```bash
pytest -m "not integration" -q 2>&1 | tail -5
```

和检查点表头的"单元测试"一行比对。

**不一致就以实跑结果为准，并明确告知用户差异。** 检查点说绿、实跑是红，
说明中间有人改了东西 —— 这件事本身比检查点里的任何内容都重要。

### 3·5. 读一遍 `.kb/decisions.md`

```bash
cat .kb/decisions.md
```

它是只追加的，**不需要校验**（历史条目不会因为 HEAD 变了而失效）。
里面是做过的范围决定，尤其是**否决项与其理由**。

**这一步不能跳**：否决项的作用就是防止被重新实现。如果用户提出的需求
在这里已经有否决记录，先把理由摆出来，而不是动手 —— 除非理由本身已经不成立
（例如当时否决的前提变了），那也要先说清楚哪一条前提变了。

### 4. 按需加载文档

只读检查点第 4 节点名的那几节，加上 `AGENTS.md`（常驻约定）。
**不要通读 `docs/prd.md`** —— 它约 1200 行，路由表在 `AGENTS.md` 第二节。

### 5. 向用户复述三句，然后等确认

1. 上次停在哪一步（检查点第 1 节）
2. 校验结果：检查点有效 / 已过期，以及实跑测试的真实状态
3. 建议的下一步（检查点第 4 节），**如果校验发现过期，说明你为什么改了建议**

确认后再动手。**检查点已过期时尤其不要直接开干** —— 先让用户知道状态变了。

## 禁止

- **不要跳过第 2、3 步**。省掉校验是这个机制唯一的失败模式
- **不要"修复"检查点让它看起来对**。它过期了就说过期，然后按实况工作，收尾时用 `ck-save` 覆盖掉
- **不要把检查点第 3 节（卡住的决策）当成已决**。那里只有编号，结论在 PRD §13 和决策台账里，以后者为准
- **不要因为检查点里写了某个方案被否决就完全不再考虑** —— 如果 HEAD 已变，否决理由可能已经不成立了，先看理由还站不站得住
