## 1. 问题定义 / Problem Statement

### 1.1 核心命题

> **删除一份源文档 ≠ 删除其中的个人信息。**
> *Deleting a source document does not delete the personal information inside it.*

在传统 CMS 里，删除是一次 `DELETE FROM documents WHERE id = ?`。在 RAG 系统里不是——因为原文在进入系统后被**复制、变形、派生**了多次，每一次都产生一个独立的副本，且这些副本分布在不同的存储引擎里，各有各的删除语义。

### 1.2 PRD 说"七处"，实际是十处

PRD v1.1 的 FR-12-04 曾列举七个位置（v1.2 起已修正为十处）。**这个数字是错的，偏少。** 完整清单：

| # | 位置 / Location | 存储引擎 / Engine | 为什么容易被漏掉 / Why it gets missed |
| --- | --- | --- | --- |
| 1 | 原文缓存 | 对象存储 | 对象存储常开版本控制，删了还有历史版本 |
| 2 | Chunk 存储 | 关系库 / 文档库 | — |
| 3 | 向量索引 | 向量库 | **软删除不等于物理删除**，见 §5.3 |
| 4 | 检索缓存 | Redis 类 | 缓存键通常按 query 哈希，无法按 chunk 定点失效 |
| 5 | 会话历史 | 关系库 | **别人的会话里也可能有该主体的信息** |
| 6 | 答案与引用记录 | 关系库 | 引用悬空问题 |
| 7 | 审计日志 | 日志库 | **与防篡改和留存义务直接冲突** |
| 8 | **备份与归档** | 备份介质 | 无法就地改写，见 §6.3 |
| 9 | **精选问答 CuratedQA** | 关系库 | 专家把含 PII 的答案固化成了标准答案（FR-05-17） |
| 10 | **评测集 EvalCase** | 关系库 | 点踩样例被一键加入评测集（FR-10-07），PII 就此进了数据集 |

第 8、9、10 项是本设计相对 PRD 的修正。**9 和 10 尤其隐蔽**：它们是产品自己的功能主动把内容复制出主链路的，谁也不会想到去清理一个"评测集"。PRD 需同步修订。

### 1.3 三个特有难点

**难点 A：向量不是脱敏后的产物。**
一种常见误解是"向量是数字，不算个人信息，留着无妨"。这是错的——嵌入向量可被**部分逆向还原**为原文（embedding inversion，如 vec2text 类方法已证明可从句向量恢复出高度近似的原句）。因此向量本身应按个人信息对待，**必须物理删除，而不是查询时过滤掉**。

**难点 B：日志的留存义务与删除权直接冲突。**
FR-09-09 要求日志防篡改，FR-09-07 要求留存 ≥6 个月（金融基线可达 5 年）。而删除权要求清除其中的个人信息。硬删日志会破坏哈希链并违反留存义务；不删则违反删除权。**这不是可以两头讨好的问题，需要一个明确的技术出口**——见 §6。

**难点 C：源系统还在，删了会自己长回来。**
从索引里删掉文档 X，下一次同步时连接器发现源系统里 X 还在、且"本地没有"，于是重新入库。删除在下个同步周期被静默撤销。**必须有墓碑机制**——见 §7。

## 3. 删除请求的四种来源 / Trigger Sources

不同来源的删除，**范围解析方式完全不同**，这是设计的第一个分叉点。

| 来源 / Source | 触发方 | 范围解析依据 | 时限 | 是否需身份核验 |
| --- | --- | --- | --- | --- |
| **T-1 数据主体请求** | 个人（员工/客户） | **主体反向索引**（§4.1） | ≤15 个工作日（可配） | **是**，见 §10.1 |
| **T-2 源文档删除传播** | 连接器同步（FR-01-11） | doc_id 精确定位 | ≤15 分钟 | 否 |
| **T-3 保留期到期** | 定时任务 | 保留策略 + 时间戳 | 到期即执行 | 否 |
| **T-4 合规下架 / 紧急** | 管理员（FR-08-03） | 人工指定 doc/目录 | ≤1 分钟 | 否，但需双人复核（FR-06-16） |

**T-1 是最难的**，因为输入是"一个人"，而系统里没有任何一张表以"人"为主键存放着他散落各处的痕迹。T-2/T-3/T-4 输入的是 doc_id，是精确的。

## 4. 核心设计 / Core Design

### 4.1 主体反向索引 / Subject Reverse Index

**没有这个索引，T-1 类请求只能全库扫描——1000 万 chunk 逐条跑 PII 识别，单次请求耗时以天计，且无法保证召回完整。**

**设计：** 在入库时（FR-12-01 PII 识别）就同步维护一张反向索引，把识别出的主体标识映射到它出现的所有位置。

```
SubjectIndex
  subject_key      -- 主体标识的 HMAC，不存明文（见下）
  subject_type     -- id_card | phone | bank_card | email | name+dob | employee_id
  location_type    -- chunk | session | answer | curated_qa | eval_case | log
  location_id
  confidence       -- PII 识别置信度
  first_seen_at
  last_seen_at
```

**关键设计决策：`subject_key` 存 HMAC 而非明文。**

反向索引若存明文身份证号，它本身就是一张高浓度 PII 表，是全系统最值得攻击的目标。改为存 `HMAC-SM3(normalized_pii, pepper)`，pepper 存于密码模块（FR-11-04）：

- 查询时：拿到请求方提供的身份证号 → 同样归一化并 HMAC → 精确匹配 → 得到所有 location
- 攻击者拖走索引表：拿到一堆哈希值，无 pepper 无法反查
- 代价：**不支持模糊匹配**（"张三" 和 "张 三" 需靠归一化对齐），且无法枚举"系统里都有谁"

**归一化规则必须固定并版本化**——大小写、空格、分隔符、手机号国际区号。归一化规则一改，历史索引全部失配，必须重建。

### 4.2 覆盖率的诚实边界

反向索引的召回率**上限等于 PII 识别（FR-12-01）的召回率**。识别不出来的 PII，索引里就没有，删除时也就找不到。这一点必须写进 DPIA 和对客说明，不能宣称"100% 删除"。

缓解手段：

1. 主体请求时**同时**做一次针对性全文检索（用主体提供的标识做 BM25 精确匹配），兜底捞出索引漏掉的
2. 识别模型升级后，对存量数据重新打标并补充索引
3. 删除证明中**明示**核查范围与方法，而非笼统声称"已彻底删除"

### 4.3 总体流程

```
删除请求
   │
   ├─[T-1] 身份核验 ────────┐
   │                        │
   ├─[T-2/T-3/T-4] 直接受理 ┤
   │                        ▼
   │                  ┌───────────┐
   │                  │ 范围解析   │ ← 主体反向索引 + 兜底全文检索
   │                  └─────┬─────┘
   │                        ▼
   │                  ┌───────────┐
   │                  │ 法定保留   │──有保留义务──→ 转「限制处理」(§8)
   │                  │ 冲突检查   │
   │                  └─────┬─────┘
   │                        │ 无冲突
   │                        ▼
   │        ┌───────────────────────────────┐
   │        │   十处清除（幂等、可重入）      │
   │        │  1-6 硬删除   7-8 加密擦除     │
   │        │  9-10 硬删除  + 墓碑写入        │
   │        └───────────────┬───────────────┘
   │                        ▼
   │                  ┌───────────┐
   │                  │ 校验探针   │ ← 逐位置回查，见 §12
   │                  └─────┬─────┘
   │                        ▼
   │                  ┌───────────┐
   └─────────────────→│ 删除证明   │→ 归档（保留 ≥3 年，PIPL 56）
                      └───────────┘
```

## 5. 十处清除的具体技术 / The Ten Purge Locations

### 5.1 原文缓存（对象存储）

- 删除对象 + **删除所有历史版本**（若桶开启了版本控制）
- 删除分片上传残留（未完成的 multipart upload）
- 若使用软删除/回收站策略，需**同步清空回收站**，或对该桶关闭软删除
- 生命周期规则不能作为删除手段——它是异步的、无确定时限的

**陷阱**：很多对象存储默认开启版本控制，`DELETE` 只是加了一个 delete marker，原对象仍在。必须用 `DeleteObjectVersion` 逐版本删。

### 5.2 Chunk 存储

- 按 `chunk_id` 硬删除，级联删除元数据、位置锚点
- **不使用软删除标记**（`is_deleted = 1`）——违反等保 8.1.4.10 剩余信息保护
- 数据库层面注意：删除后的页面可能仍在磁盘上，需依赖 §6 的加密擦除作为兜底

### 5.3 向量索引 — 最容易做错的一环

**问题：主流向量库的 `delete` 都是软删除。**

- Milvus：`delete` 写入删除标记，实体在 **compaction** 后才从 segment 中物理移除；被丢弃的 segment 还可能留在对象存储里
- Qdrant：`delete` 标记点为删除，实际移除发生在 **optimizer 触发 segment 重建**时

因此正确流程是三步，**缺一不可**：

```
1. delete(chunk_ids)              -- 逻辑删除
2. force_compaction() / optimize() -- 强制段合并，物理移除
3. verify_segments()               -- 确认旧 segment 已被回收
```

**还必须处理：**

| 项 / Item | 处理 / Handling |
| --- | --- |
| **副本 Replica** | 所有副本节点都要 compaction，不能只处理主节点 |
| **内存缓存** | 已加载到内存的 segment 需卸载重载 |
| **快照 Snapshot** | 向量库自身的快照文件按备份处理（§6.3） |
| **旧模型索引** | FR-03-07 支持双索引灰度，切换期间**两套索引都要删** |

**为什么不能"查询时过滤掉"**：见 §1.3 难点 A。向量可被部分逆向，留着就是留着个人信息。过滤只是不让它出现在结果里，不是删除。

### 5.4 检索缓存

**前置改造**：缓存必须建立 `chunk_id → cache_key[]` 的反向映射，否则无法定点失效，只能整体 flush。

- 定点失效：按反向映射删除受影响的缓存条目
- 兜底：删除操作触发缓存**版本号自增**，旧版本条目全部失效
- **缓存不按用户权限分区**（PRD v1.7 **FR-04-14a**）。反向映射就是
  `chunk_id → cache_key[]`，量级 = chunk 数 × 平均复用次数，**与用户数无关**。
  （按权限分区的 FR-04-14b 是 P2 且在本期不做清单 N-6 里。本文 v1.0 写的
  "按用户权限分区、同一 chunk 存在于多个分区"是 v1.6 拆分 14a/14b 之前的旧语义，
  照它实现会把反向映射按权限组数放大，且可能假设分区存在而漏失效。）
- 若将来启用 14b，本节须同步修订：分区后同一 chunk 会出现在多个分区条目中，
  定点失效必须遍历全部分区

### 5.5 会话历史

**这里有一个反直觉的点：不能只删该主体本人的会话。**

场景：员工 A 问"张三的联系方式是多少"，系统答了。张三申请删除。此时 PII 在 **A 的会话历史**里，不在张三的。按主体反向索引查 `location_type = session` 才能定位到。

处理方式：

- **默认脱敏而非删整条**：把会话中的 PII 片段替换为 `[已依法删除]`，保留会话结构。整条删除会破坏 A 的使用体验，且 A 的提问行为本身是 A 的数据，不是张三的
- 若整条会话的存在本身即构成对该主体的处理（如"关于张三的调查记录"），则整条删除
- FR-12-16 若启用匿名化统计模式，会话原文本就不留存，此处工作量大幅降低

### 5.6 答案与引用记录

- 答案文本按 §5.5 同样脱敏
- **引用悬空处理**：`Citation` 指向已删除的 chunk，UI 上不能报错或显示空白，应显示「引用来源已依法删除」并禁用跳转
- 引用记录本身保留（它是"当时依据什么作答"的证据），仅指向的内容不可达

### 5.7 审计日志

**不能硬删。** 硬删会同时违反：

- FR-09-09 日志防篡改（哈希链断裂）
- FR-09-07 留存义务（6 个月 / 金融 5 年）
- 等保 8.1.4.3 c) 审计记录防止未预期删除

**解法：加密擦除**（§6）。日志记录结构完整保留，哈希链完整，但其中的 PII 字段因密钥销毁而不可读。审计功能（谁在什么时间做了什么）不受影响。

### 5.8 备份与归档

见 §6.3。这是全系统**唯一无法做到即时物理清除**的位置，必须靠加密擦除 + 抑制清单组合应对。

### 5.9 精选问答 CuratedQA

专家通过 FR-05-17 把答案固化为标准答案时，PII 被复制进了一张独立的表，且这张表**优先于检索返回**——意味着删除没做干净的话，PII 会被优先命中。

- 按主体反向索引定位并脱敏
- 脱敏后触发该条目**重新审核**（内容可能已不完整，专家需确认是否仍有效）

### 5.10 评测集 EvalCase

FR-10-07 允许把用户点踩样例一键加入评测集。这条路径会把**真实的、含 PII 的问答对**沉淀进一个长期保留、反复使用、还可能被导出分享的数据集。

- 按主体反向索引定位并删除对应 case
- 删除后评测集规模变化 → 触发基线重算标记，避免与历史评测结果误比较
- **建议同时增加一条产品约束**：入评测集时强制走一次 PII 脱敏，从源头降低此路径的风险

## 6. 加密擦除 / Crypto-Shredding

### 6.1 原理

对无法物理删除的位置（日志、备份），采用**密钥销毁**代替数据销毁：

```
入库时：  PII 字段 → 用「主体级数据密钥 DEK_subject」加密后存储
          DEK_subject → 被 KEK 包裹，KEK 存于密码模块（FR-11-04/05）

删除时：  销毁 DEK_subject
          → 密文仍在日志/备份里，但已无法解密
          → 日志记录结构、哈希链、留存义务均不受影响
```

这与 FR-11-05 的密钥分层管理是同一套基础设施，不需要额外引入组件。

### 6.2 适用边界 —— 必须诚实说明的三点

**加密擦除在多数监管实践中被接受为等效于删除，但不是普遍无条件成立的。** 三个前提必须成立，否则不能声称已删除：

1. **同一 PII 不得在别处以明文存在。** 若日志里加密了、但缓存里是明文，加密擦除无意义
2. **密钥销毁本身必须可验证、不可恢复。** 密钥若有备份副本（包括密码模块自身的备份），销毁就是假的。需要密码模块提供可审计的密钥销毁记录
3. **算法在可预见期内不被攻破。** 这一点无法绝对保证，属于残余风险，应在 DPIA 中记录

**因此**：加密擦除的采用须经法务与客户合规官书面确认，并写入 DPIA。产品不应默认宣称"加密擦除 = 删除"。

### 6.3 备份的处理

备份介质无法就地改写，这是物理事实。组合方案：

| 手段 / Measure | 说明 / Detail |
| --- | --- |
| **加密擦除** | 备份中的 PII 随 DEK 销毁而不可读——主要手段 |
| **抑制清单** | 若备份被恢复，恢复流程强制比对抑制清单（§7），已删对象不重新进入索引 |
| **轮转过期** | 明示备份轮转周期（如 90 天），届时含旧数据的备份自然失效 |
| **限制处理声明** | 依 PIPL 47¶2，对备份中"技术上难以即时删除"的部分，声明已停止除存储和安全保护外的一切处理 |

**对客话术必须准确**：不说"备份里也删干净了"，而说"备份中的相关数据已通过密钥销毁失去可读性，并已停止除存储外的一切处理；备份介质将在 N 天轮转周期内自然过期"。前者可能是虚假陈述，后者是可举证的事实。

## 7. 墓碑与抑制清单 / Tombstone & Suppression List

### 7.1 问题

删除后，下一次连接器同步会发现源系统里文档还在、本地没有，于是**重新入库**。删除被静默撤销，且没有任何告警。

这个 bug 的特征是：删除验收当天测试通过，一周后 PII 又回来了。

### 7.2 设计

```
SuppressionList
  suppression_id
  scope_type       -- document | subject | chunk_hash
  scope_key        -- HMAC(source_id + external_id) 或 HMAC(subject_pii)
  reason           -- erasure_request | retention_expired | admin_takedown
  created_at
  expires_at       -- NULL = 永久
  source_confirmed -- 源系统是否已确认删除
```

**执行点**：连接器入库前（FR-01 流水线阶段 ①）与索引构建前（阶段 ③）各校验一次。命中即跳过，并记录一条"已抑制"事件。

**同样存 HMAC**：抑制清单本身是一张"哪些人要求过删除"的名单，明文存放等于制造了一个新的敏感数据集。

### 7.3 抑制条目何时可以移除

| 情形 / Case | 处理 / Handling |
| --- | --- |
| 源系统确认已删除 | `source_confirmed = true` 后可移除（源头没有了，不会再同步进来） |
| 源系统仍保留 | **永久保留抑制条目**，否则删除会失效 |
| 主体撤回删除请求 | 需二次身份核验后方可移除 |
| 索引全量重建（FR-03-08） | 抑制清单**必须先于重建加载**，否则重建会把删掉的全捞回来 |

> **重建索引是删除失效的第二个高发场景。** 抑制清单的加载必须写进重建任务的前置步骤，且重建完成后要跑一次校验探针。

## 8. 限制处理状态 / Restricted Processing

### 8.1 何时进入此状态

当删除请求与**法定保留义务**冲突时——依 PIPL 第 47 条第二款与 GDPR 第 18 条，这是法律明确提供的处理路径，不是规避：

- 法定保留期未届满（如金融业务记录、审计日志）
- 正在进行的诉讼、调查、监管检查（legal hold）
- 技术上难以即时删除（备份介质）

### 8.2 状态语义 —— "停止除存储和必要安全保护以外的处理"

| 行为 / Behavior | 限制处理状态下 |
| --- | --- |
| 参与检索召回 | **禁止** |
| 参与答案生成 | **禁止** |
| 进入评测集 / 精选问答 | **禁止** |
| 被导出、分享、推送 | **禁止** |
| 用于统计分析 | **禁止** |
| 存储 | 允许（这是保留义务本身要求的） |
| 安全保护措施（加密、备份、访问控制） | 允许且必须 |
| 人工访问 | **需 break-glass**：双人审批 + 全程审计 + 事后通知合规官 |

### 8.3 状态退出

保留期届满 → 定时任务自动触发真正的删除（T-3），无需主体二次申请。**这一点必须自动化**，否则限制处理会成为一个永不结束的中间态，实质上等于没删。

## 9. 删除状态机 / State Machine

```
                    ┌──────────┐
                    │ RECEIVED │  请求受理
                    └────┬─────┘
                         │ 身份核验（仅 T-1）
                         ▼
                    ┌──────────┐      核验失败
                    │ VERIFYING│──────────────→ REJECTED
                    └────┬─────┘                 （说明理由，PIPL 50）
                         ▼
                    ┌──────────┐
                    │ SCOPING  │  范围解析：反向索引 + 兜底检索
                    └────┬─────┘
                         ▼
                    ┌──────────┐
                    │  SCOPED  │  产出待删对象清单
                    └────┬─────┘
                         │
              ┌──────────┴──────────┐
              │ 保留义务冲突检查      │
              ▼                     ▼
      ┌──────────────┐      ┌──────────────┐
      │  EXECUTING   │      │  RESTRICTED  │ 部分对象转限制处理
      │  十处清除     │      │  （§8）      │ 保留期届满后自动回到 EXECUTING
      └──────┬───────┘      └──────────────┘
             │ 部分失败
             ├────────────→ PARTIAL_FAILED ──重试──┐
             │                                     │
             ▼                                     │
      ┌──────────────┐                             │
      │  VERIFYING2  │  校验探针逐位置回查           │
      └──────┬───────┘                             │
             │ 探针发现残留                          │
             ├─────────────────────────────────────┘
             ▼
      ┌──────────────┐
      │  CERTIFIED   │  生成删除证明
      └──────┬───────┘
             ▼
      ┌──────────────┐
      │   CLOSED     │  证明归档（≥3 年，PIPL 56）
      └──────────────┘
```

**幂等性要求**：每个位置的清除操作必须幂等——重试不报错、不产生副作用。状态机可从任意中断点恢复，已完成的位置跳过。

**超时告警**：请求进入 `EXECUTING` 超过配置阈值（默认 72h）未完成 → 告警，防止请求悄无声息地卡死直到超出法定时限。

## 10. 边界情况 / Edge Cases

### 10.1 请求方身份核验 —— 删除接口本身是攻击面

**两个方向的风险：**

- **恶意删除**：攻击者冒充他人申请删除，造成数据破坏
- **信息刺探**：攻击者提交任意身份证号，从"找到 N 条记录"或"未找到"的响应中反推该人是否为本机构客户

**设计：**

1. 身份核验必须走客户已有的可信通道（SSO、实名认证、线下工单），**不做自助式匿名提交**
2. 响应**不区分**"未找到"与"已受理"——统一返回"请求已受理，处理完成后将另行通知"，杜绝存在性刺探
3. 删除是不可逆操作，建议设置**冷静期**（如 24h）并向主体已验证的联系方式发送确认通知，给误操作和冒充留出发现窗口
4. 全过程记入审计日志（该日志本身受 §5.7 保护）

### 10.2 并发查询

删除执行期间，某用户正在检索，命中了正在被删的 chunk。

- 清除顺序设计为**先切断可达性，再物理删除**：先失效缓存 + 从检索路径摘除 → 再删向量 → 再删 chunk → 再删原文
- 已在生成中的会话：允许当次完成（证据已在上下文里），但不写入答案记录

### 10.3 删除请求记录本身含 PII

`ErasureRequest` 表要保留 3 年作为合规证据，但它记录着"某某要求删除"——本身就是敏感信息。

- 请求记录中仅存 `subject_key`（HMAC）+ 最小必要字段
- 主体明文标识用 §6 的加密擦除保护，证明归档后即销毁 DEK，只留可核验的哈希

### 10.4 一次请求跨多租户

多租户实例（FR-03-09）中，同一主体可能出现在多个租户的知识库里。

- **默认不跨租户执行**——租户 A 的管理员无权删除租户 B 的数据
- 跨租户删除须由平台管理员发起，且分别向各租户合规官通报

### 10.5 已导出/已分享的内容

答案曾被导出为 PDF（FR-07-09）或分享给他人（FR-07-08）。系统无法追回已下载的文件。

- 依 GDPR 第 19 条，需**通知已知的下游接收方**
- 系统侧：失效所有分享链接；导出记录中标注"内容已依法删除"
- 对客说明中明示：已被本地下载的副本不在系统控制范围内

### 10.6 删除后源系统又更新了该文档

源文档被修改后重新同步，内容可能已不含被删的 PII。

- 抑制清单按 `HMAC(source_id + external_id)` 抑制的是**该文档**，会连新版本一起挡掉
- 若需放行，须人工复核新版本确认 PII 已移除后，手工移除抑制条目
- **默认从严**：宁可挡住也不放行

## 11. 删除证明 / Deletion Certificate

FR-12-05 要求"可核验的删除报告"。内容清单：

| 字段 / Field | 说明 / Detail |
| --- | --- |
| 证明编号 | 唯一 ID |
| 请求来源 | T-1 ~ T-4 |
| 主体标识 | **HMAC 值**，不含明文 |
| 受理时间 / 完成时间 | 用于证明满足时限 |
| **核查范围与方法** | 反向索引 + 兜底检索的具体口径 —— **这一栏是诚实性的关键** |
| 已清除对象清单 | 按十处位置分列，各列对象数量与类型 |
| 加密擦除对象 | 哪些位置采用了密钥销毁，密钥销毁凭证 |
| 转限制处理的对象 | 数量、原因、法定保留期届满日 |
| 校验探针结果 | 逐位置的回查结论 |
| **未覆盖范围声明** | 已下载副本、PII 识别召回率上限等 |
| 执行人 / 复核人 | 双人 |
| 完整性校验值 | 证明本身的哈希，防篡改 |

**"未覆盖范围声明"不能省略。** 一份声称"已 100% 彻底删除"的证明，在监管核查发现任何残留时，会从有利证据变成不利证据。写明边界的证明反而更经得起检验。

## 12. 验证方法 / Verification

这一节直接产出 **DL-8 删除权链路验证报告**。

### 12.1 Canary 探针法

**思路**：注入一个合成的、绝不会自然出现的假身份，让它走完整条链路，然后删除，再从十个位置逐一回捞。

```
① 构造 canary 主体
   身份证号、手机号、姓名均为合成且全局唯一
   （如 "钟离无咎"、手机 199-0000-0001）

② 让它遍历所有十个位置
   - 上传含该 PII 的文档 → 位置 1,2,3
   - 发起检索使其进入缓存 → 位置 4
   - 多轮问答 → 位置 5,6
   - 触发审计日志 → 位置 7
   - 执行一次备份 → 位置 8
   - 专家固化为精选答案 → 位置 9
   - 点踩并加入评测集 → 位置 10

③ 发起删除请求

④ 直接探针：逐位置技术回查
   - 对象存储：列出所有版本
   - 数据库：全表 LIKE 检索
   - 向量库：用原始 embedding 做 top-1000 相似检索
   - 缓存：全量 key 扫描
   - 日志：grep 明文
   - 备份：恢复到隔离环境后检索
   - 精选问答 / 评测集：全表检索

⑤ 间接探针：从产品外部尝试套取
   用 20 组诱导性问题向助手提问
   （"钟离无咎的手机号"、"上个月谁问过钟离无咎"、
     "列出所有姓钟离的人"…）

⑥ 断言：直接与间接探针的召回均为 0
```

### 12.2 必须包含的负向用例

只测"删得掉"是不够的，还要测"删了不会自己回来"：

| 用例 / Case | 验证点 |
| --- | --- |
| 删除后触发一次源系统同步 | 抑制清单生效，未重新入库（§7） |
| 删除后执行索引全量重建 | 重建前加载抑制清单，未捞回（§7.3） |
| 删除后从备份恢复 | 恢复流程比对抑制清单，未重新进入索引 |
| 删除执行中途强制中断，再重启 | 幂等恢复，最终一致 |
| 同一请求重复提交 3 次 | 幂等，不报错，不重复计费/计数 |
| 处于法定保留期的对象 | 正确转入限制处理，且检索不可达 |
| 限制处理对象保留期届满 | 自动触发真删，无需二次申请 |

### 12.3 自动化与频率

- 全套探针脚本化，纳入 CI，**每次大版本发布前必跑**
- 每年执行一次完整版（含备份恢复验证），产出 DL-8
- 向量库、缓存组件版本升级后必须重跑——软删除语义可能随版本变化

## 13. 性能与容量影响 / Performance Impact

| 项 / Item | 影响 / Impact | 缓解 / Mitigation |
| --- | --- | --- |
| 向量库 compaction | 重 I/O，大索引可能耗时数十分钟 | 批量合并删除请求，在低峰窗口执行；15 工作日的 SLA 留足了批处理空间 |
| 紧急删除（T-4） | 无法等批处理窗口 | 提供加急通道：先切断可达性（缓存失效 + 检索摘除，秒级），物理清除随后异步完成 |
| 反向索引存储 | 每个 PII 实例一行，PII 密集语料下可能达到 chunk 数的数倍 | 按 confidence 阈值过滤低置信条目；定期归并 |
| 入库延迟 | PII 识别 + 索引写入增加单文档处理时间 | 异步化，不阻塞主索引构建 |
| 备份体积 | 加密擦除不减少备份体积 | 明示轮转周期；这是设计取舍而非缺陷 |
